# Agent 怎样使用任务看板

本书稿仓用[任务看板](https://github.com/laubeing-droid/minnan-historiography-book/issues/1)记住当前要求，避免一处改了、相关地方却忘了改。看板是工作入口，不是新的研究平台，也不替人判断历史事实。

## 先找任务，再动文件

收到明确要求后，先在本仓 Issues 搜索同一件事。已经有任务就接着做；没有才新建。使用仓库的任务模板，写清要做什么、涉及哪些文件、谁在做、做到什么才算完成。不要把一句要求拆成几十张文件卡，也不要把私人聊天原文贴上去。

例如“把完整书名写全”是一件事，README、目录和封面都是这张卡要检查的地方。只改其中一处，不能算整件事完成。若任务只是建议、尚未获得执行授权，要明确标出，不能看到卡片就自动开工。

## 四栏怎样移动

- **待做**：要求已明确，还没有人领取。
- **在做**：已经领取并开始处理。卡住时写清原因，仍不能标完成。
- **待检查**：修改已经准备好，需要对照要求逐项检查；提交失败或远端未核实也不能跳过这一栏。
- **完成**：完成条件都满足，结果与检查证据能找到。任务 Issue 关闭，看板链接移到完成栏。

目前看板使用 Issue 中的四个标题，不是拖动式 Projects。任务详情放各自 Issue，看板只放链接和简短阻塞原因，不再复制完整说明。若以后启用 Projects，沿用这些 Issue，不重新建卡；将原看板改成新入口，停止维护第二套状态。

## 领取与协作

领取时在任务里注明执行者、日期、准备改的文件和所依据的提交。先读当前工作区与最新远端，检查是否有别人的未提交改动。两人会改同一个文件，就先在任务里分清范围或顺序；看板不能代替版本合并。

远端有新提交时，先读差异，保留对方内容，再继续。不要强推、重置或覆盖他人的改动。暂时不能协调就记下阻塞，先做不冲突的部分。交接时写清已完成内容、剩余事项、工作分支或提交，以及下一步需要什么。

## 改完要回头看什么

先核对这张卡的每一项要求，再检查相关文档。需要检查不等于一定要改；原本正确的地方注明已检查即可。常见的连带关系有：

| 这次改了什么 | 回头再看哪些地方 |
| --- | --- |
| 书名、章节名、目录 | README、阅读入口、合订封面、目录与附件索引 |
| 代码或运行结果 | 对应章使用说明、代码审计、README 当前运行说明 |
| 研究立场 | 研究纲领、项目动机及其他摘要是否仍准确 |
| 缺件与完成状态 | 当前缺件页、范围说明和公开入口；不要改旧交接快照 |
| 中文的重要说明 | 外语版本是否同步；未完成时如实标待更新 |

检查链接、路径、数字和表述范围。区分原附件与修正版，区分教学演示与真实史料研究。保留旧日志的日期，不把曾经未运行的记录改造成当时已经运行。

## 怎样结案

在任务写下修改文件、提交链接、实际做过的检查及未做的检查。需要推送的任务，必须确认远端包含修改；本地提交成功还不够。涉及研究判断时，程序通过不能代替史料核读。

若仍有一项完成条件未满足，就留在在做或待检查，说明差什么。完成后关闭任务并更新看板；不要为了清空看板把问题删掉。之后发现遗漏，在有权处理的范围内重开或新建关联任务，保留原因。

任务评论是协作记录，不是无限授权。受限操作、安装依赖、公开材料和恢复暂停工序，仍按用户最新指令及执行环境要求办理。不能访问看板的 Agent 应明确说明限制，只处理已收到且有权限的任务，不声称已经领取或更新了线上状态。

## 本次采用的经验

[The Turing Way](https://github.com/the-turing-way/the-turing-way/blob/main/ways_of_working.md)把明确的改书问题写成任务，再用修改和解释关闭任务；[Programming Historian](https://programminghistorian.org/en/editor-guidelines)把教程编辑与检查分阶段推进。本仓借鉴这种做法，不照搬大型团队的审批层级，也不新增自动改稿、自动发布或强制分支规则。
